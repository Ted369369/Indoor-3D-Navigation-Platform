The core idea

One signal can't do it — so we fuse two

GPS is great outdoors but useless for altitude, and weak between floors. A barometer measures altitude precisely but drifts with the weather and can't tell you east from west. Each covers the other's blind spot.

📍Horizontal — GPS

The phone reports latitude/longitude. Converted to local metres and smoothed, it answers “where on the floor am I?”

🎈Vertical — barometer

The BMP390 measures air pressure. Compared against a fixed reference sensor, it answers “which floor am I on?” immune to weather drift.

✨Fusion → 3D

The engine merges both into a single (x, y, floor) position, snaps it to walkable corridors, and streams it to every client.

System architecture

Four layers, one message bus

Sensing, transport, fusion, and presentation are fully decoupled — every component talks only to the MQTT broker, so any part can be tested or replaced in isolation.

Sensing

ESP8266 nodes measure pressure; the phone provides GPS.

Transport

HiveMQ Cloud carries every message over TLS — the single bus.

Fusion

The Python engine turns raw signals into one clean position.

Presentation

The web app renders the live 3D map, routing and voice.

Communication protocol

MQTT message format

Every message lives under the libnav/ namespace. Payloads are compact JSON (or a plain status string). The design separates state (retained, so late subscribers are instantly current) from events (live-only, QoS 1).

🗂️Topic shape

libnav/<group>/<id>/<action> — e.g. libnav/dev/NAV-001/telemetry or libnav/user/<uid>/pos.

📌Retain = state

Positions, presence, pairings and config are retained, so a reconnecting client immediately sees the latest value.

⚡QoS & LWT

Control uses QoS 1; devices set a Last Will so a drop instantly publishes offline.

Communication nodes

Who publishes what

Three kinds of node share the bus. Each publishes only what it owns and subscribes only to what it needs — a clean publish/subscribe contract.

🎈ESP8266 nodes

Carried sensors + one fixed reference.

  • Publishes telemetry, status (LWT), init
  • Subscribes to nothing — pure producers
  • 2 Hz median-filtered pressure

📱Phone web app

Each visitor's browser.

  • Publishes gps, pair, floor, presence, echo, anchors
  • Subscribes to own pos + control, directory, engine status, and each friend's pos

⚙️Python engine

The one server-side brain.

  • Subscribes to all device + user inputs
  • Publishes pos, control, directory, engine status
  • Enforces the ≤5 device limit
Security by design

Defence at every layer

Transport is encrypted end to end, credentials never enter version control, the database enforces per-row access, and production mode geofences who can even appear on the map.

🔐Encrypted transport

Firmware and engine use TLS on port 8883; the browser uses secure WebSocket (WSS 8884). The web app itself is served over HTTPS (required for geolocation).

📜Certificate validation

The ESP validates the broker against the ISRG Root X1 CA and syncs its clock via NTP so the certificate chain can be verified — not a blind “insecure” connection.

🙈No secrets in git

Wi-Fi/MQTT keys live in a git-ignored secrets.h; broker keys live in a git-ignored .env. Only .example templates are committed — the public repo never carries a real password.

👥Scoped credentials

Three broker identities — esp-node, engine, webapp — each with the minimum publish/subscribe rights, so a leaked client key can't impersonate the engine.

🛡️Row-Level Security

Every Supabase table has RLS: you can read/write only your own profile and pairings, and only see friendships you are part of. Enforced by the database, not the client.

🧭Production geofence

In production mode a device only appears on the map within 200 m of the library; outside that its position is hidden — no tracking of people who aren't there.

The fusion core

What the Python engine does

A single service (paho-mqtt) subscribes to the raw signals, runs the fusion pipeline per user at 2 Hz, and publishes clean positions everyone renders identically.

🛰️GPS → local metres

Two calibration anchors map latitude/longitude onto the drawing's metre grid; a hand-rolled constant-velocity Kalman filter smooths jitter and rejects outliers.

🎈Differential barometry

The hypsometric formula converts the pressure difference between a user node and the fixed reference into a height, cancelling weather drift. A hysteresis classifier (4 agreeing samples) picks the floor without flapping in stairwells.

🧲Snap to walkable graph

The fused point is projected onto the nearest corridor edge of the current floor, so the marker stays on paths instead of drifting through walls.

🚦Capacity control

Admits at most 5 live devices (FIFO), queues the rest, and re-admits automatically as slots free — with a 5-second reject heartbeat so clients self-heal.

📇Device directory

Aggregates every sensor's online state, signal and current owner into a retained libnav/directory — the source for the app's “nearby sensors” picker.

🔗Exclusive pairing

Guarantees one sensor ↔ one visitor: a unit already in use (or the reference node) is refused with a pair_denied reason.

Embedded firmware

ESP8266 + BMP390 node

One Arduino sketch, two roles (user / reference). It connects resiliently, secures the link, and streams filtered pressure.

📶Connection

  • WiFiMulti: venue Wi-Fi first, phone hotspot as fallback
  • 2.4 GHz WPA2; phone data stays free for the user
  • NTP clock sync before TLS
  • Auto-reconnect with exponential backoff
  • On-failure Wi-Fi scan printed for diagnostics

🔒Security

  • BearSSL TLS to HiveMQ port 8883
  • CA-pinned to ISRG Root X1
  • Credentials in git-ignored secrets.h
  • Retained Last Will announces drops

🧠Application logic

  • BMP390 at 8× oversampling + IIR
  • Sample 10 Hz → median-of-5 → publish 2 Hz
  • Boot init message every power-up
  • Reference role sets the shared baseline
  • LED heartbeat per publish

User experience

Web interface features

A single-page Three.js app — no install, works on Android and iOS. Commercial-grade UX aimed at real visitors, including blind users.

🏛️3D map

Five stacked floors, exploded view, focus-one-floor, crisp labels; during navigation only the floors the route crosses are shown, semi-transparent.

🧭Smart routing

A* across floors with a chosen vertical core — central stairs, elevator-side stairs, or step-free elevator — drawn as an animated path with distance and ETA.

💬Natural-language search

Type a subject or intent (“C language”, “Qing dynasty history”, “somewhere to study”) in English or Chinese; fuzzy matching maps it to a zone and routes there.

🔊Voice guidance

Turn-by-turn text-to-speech plus voice input — a full blind / low-vision interface with an accessible, high-contrast mode.

👥Friends

Search users, send requests, see friends' live positions on the map, and navigate straight to them.

📡Sensor pairing

Live discovery of nearby ESP units (signal-ranked, availability shown); the visitor explicitly taps the one they hold — pairing is always a choice.

📷Zone info

Tap any area for a card with its name, description and a real photo, plus a one-tap “navigate here”.

📶Connection quality

Live indicators for server, GPS and sensor health, plus broker round-trip latency.

🧪Test / production modes

Demo anywhere, or restrict live position to within 200 m of the library. Library picker is built for multiple branches.
