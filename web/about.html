Finding your floor inside a library

Library Nav shows where you are inside a library on a 3D map and walks you to a shelf, a desk or a friend. Your phone's GPS gives the position on the floor. A small pressure sensor you carry works out which floor you are on. Two libraries are mapped so far: the Taipei Public Library Main Library and the Yorba Linda Public Library in California.

01

Why two sensors

Phone GPS is fine for "which side of the building", but it has no useful idea of height. Indoors the vertical error is easily bigger than one floor.

Air pressure drops by roughly 12 Pa per metre, so a BMP390 can see the 3.8 m between floors clearly. On its own, though, the reading drifts with the weather and says nothing about where you are on the floor. So the two are combined.

GPS (phone)

Latitude and longitude, turned into metres on the floor plan and smoothed.

Pressure (BMP390)

Compared with a second sensor fixed on 1F, which cancels out weather changes.

Combined

One position: x and y in metres plus a floor number, kept on walkable paths.

02

How it fits together

Nothing talks to anything directly. Sensors, phones and the position engine all connect to one MQTT broker (HiveMQ Cloud), which made it easy to test each piece on its own, for example running the engine against a simulator before the hardware worked.

03

MQTT messages

Every topic starts with libnav/ and then names the kind of sender, its id and what the message is, for example libnav/dev/NAV-001/telemetry or libnav/user/<uid>/pos. Payloads are small JSON objects, or just online/offline.

One rule decides the flags. If a message describes the current state (a position, who is online, how many slots are used), it is retained, so a phone that reconnects sees it straight away. If it is an event (a sensor sample, "you were admitted"), it is not retained, because replaying an old event later would be wrong. Devices also register a Last Will, so the broker publishes offline for them if they drop.

Sensors never listen to anything. That keeps the firmware simple: it connects, samples and publishes, and does not need to handle commands.

05

Security

  • Encrypted links. The sensors and the engine use MQTT over TLS on port 8883. Browsers use secure WebSockets on 8884. The site itself is served over HTTPS, which browsers require before they hand out GPS.
  • The certificate is checked. The ESP8266 verifies the broker against the ISRG Root X1 certificate and gets the time from NTP first, because a certificate can't be validated without a clock. If certs.h still has no certificate, the link is encrypted but the broker isn't verified, and the serial log prints a warning saying so.
  • No secrets in the repository. Wi-Fi and broker passwords for the sensors live in secrets.h, and the engine's in backend/.env. Both are in .gitignore; only example files are committed.
  • Separate broker accounts. Sensors, the engine and the web app each log in with their own account and permissions. The web app's password is public by nature (it ships in the page), so that account may only publish under libnav/user/ and libnav/site/. It can't fake sensor readings, the sensor list or the engine's status.
  • Row-level security. Every Supabase table has RLS turned on. You can only change your own profile and pairings and only see friendships you are part of, and the database enforces that, not the app.
  • Geofence in production mode. A position is only shown when the phone is within 200 m of the library, so the app doesn't track people who aren't there.
06

The position engine

One Python process using paho-mqtt. It loads every library in libraries.json and keeps a separate map, reference sensor, calibration and user limit for each. Phones say which library they're in (lib in their messages) and sensors say which one they belong to (site). For each connected user it runs these steps twice a second and publishes the result to user/<uid>/pos, so every screen draws the same position.

  1. GPS to metresTwo calibration points tie latitude and longitude to the metre grid of the floor plan. A small constant-velocity Kalman filter smooths the jitter and throws away jumps that aren't physically possible.
  2. Height from pressureThe hypsometric formula turns the pressure difference between your sensor and the reference sensor on 1F into a height. Using the difference means the weather cancels out.
  3. Pick a floorThe floor only changes after 4 samples in a row agree, so standing on the stairs doesn't make the marker flicker between floors.
  4. Snap to pathsThe point is moved to the nearest corridor on that floor, so the marker doesn't drift through walls or shelves.
  5. Limit to 5 sensorsIn each library the first 5 users are admitted and the rest wait in order. When someone leaves, the next person is let in automatically. Rejected clients are reminded every 5 seconds, so a phone that missed the message still recovers.
  6. Keep the sensor listThe engine publishes which sensors are online, their signal and whether someone is using them. The app's sensor picker reads this, and a sensor that is already taken is refused with pair_denied.
07

Sensor firmware

One Arduino sketch for the ESP8266 with a BMP390 on I²C. Compile-time settings make a unit either a carried sensor or the fixed reference, and say which library it belongs to (SITE_ID).

Connecting

  • WiFiMulti tries the library Wi-Fi first and a phone hotspot second (2.4 GHz only).
  • Clock sync over NTP before the TLS handshake.
  • Reconnects with a growing delay instead of hammering the broker.
  • Logs the Wi-Fi disconnect reason and the last reset reason over serial, which is how the reboot loop below was found.

Measuring

  • BMP390 with 8× pressure oversampling and the built-in IIR filter.
  • Reads 10 times a second, takes the median of the last 5 and publishes twice a second.
  • Sends an init message with firmware build, IP, reset reason and free memory on every boot.
One bug worth mentioning. The first TLS version rebooted forever right after connecting to Wi-Fi. The CA certificate was stored in flash (PROGMEM) and handed straight to BearSSL, which reads it like normal RAM and crashes on the ESP8266. Copying it into RAM first fixed it. This and the other problems are written up in docs/TROUBLESHOOTING_LOG.md.

HiveMQ Cloud and Supabase

The MQTT broker. A hosted one means there's no server to keep patched, and TLS works out of the box.

09

The web app

A single page built on Three.js, hosted on GitHub Pages. Nothing to install; it runs in the browser on Android and iPhone.

Libraries
Pick the library on the first screen. Each one is a single model file with its floors, rooms, paths, stair names and search words, so adding a building doesn't need code changes. How the two maps were made.
3D map
All floors stacked, or spread apart, or one floor at a time. Zone codes in the overview, full names once you pick a floor.
Routes
A* across floors. A route keeps to one staircase (in Taipei the central stairs or the stairs next to the elevator, in Yorba Linda the grand staircase or the west stairs), or uses only the elevator for step-free routes. While navigating, only the floors on the route are shown.
Search
Type a subject, a book or a place in English or Chinese: "C language" or "Qing dynasty" in Taipei, "cooking" or "storytime" in Yorba Linda. Fuzzy matching maps it to an area and starts the route.
Voice
Spoken turn-by-turn directions and voice input, plus a low-vision mode with larger controls.
Friends
Find people by name, send a request, see accepted friends on the map and get a route to them.
Sensor pairing
Lists the sensors that are online, sorted by signal, with the ones in use greyed out. You always pick yours; nothing pairs automatically.
GPS only
No sensor? Start in GPS-only mode and set your floor from a menu.
Zone cards
Tap an area to see its name, what's there, a photo and a button to go there.
Status
Indicators for the broker, GPS and sensor, the round-trip latency, and how many of the 5 sensor slots are taken.
